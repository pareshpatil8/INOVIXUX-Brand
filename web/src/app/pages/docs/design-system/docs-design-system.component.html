Design system

Verified Line is the shared visual and interaction language for INOVIXUX. Start with the foundations below, try the working controls, then open the component library for inputs, defaults and accessibility contracts.

Foundations

Typography

Geist is the website's heading, body and control font, through --ino-font-display. Noto Sans Devanagari and system sans-serif faces provide fallbacks. Geist Mono (--ino-font-mono) is reserved for code, metrics and compact metadata. Use the type roles rather than selecting a new font or size for each screen.

  • --ino-type-display, --ino-type-h2 and --ino-type-h3: heading hierarchy.
  • --ino-type-body and --ino-type-body-lg: reading text and introductions.
  • --ino-type-label, --ino-type-hint and --ino-type-caption: control labels and supporting text.

Color and themes

Use semantic pairs: --ino-color-surface with --ino-color-on-surface, and status tokens for success, warning and danger. Avoid raw hex colors in components. The site theme control switches between dark, light and high contrast; check every state in all three. Always pair status color with a readable label or icon meaning.

Spacing, density and motion

Layout uses --ino-space-*, corners use --ino-radius-*, and transitions use --ino-motion-duration-*. Dense layouts compact information without removing labels or keyboard focus. Controls use the shared sm | default | lg size axis where supported; use the individual component's API to check availability. Honor reduced-motion preferences and keep feedback understandable without animation.

Use the components

Import the standalone Angular component into the consuming component's imports, load the shared token stylesheet once, and bind state in your application. For example, import InoButtonComponent from web/src/app/components/button/ino-button.component.ts when working in this repository, then use its attribute on a native button: 

<button ino-button variant="primary" type="button">Save changes</button>

The examples below run locally in this page; they do not save data or send notifications. Structural components such as navigation, hero and cards can also be seen on the homepage.

Buttons

Use primary for the main action, secondary for alternatives, ghost for low emphasis and danger for destructive actions. Icon-only buttons need an accessible name. Loading and disabled states block activation.

Form controls

Labeled, with WCAG 2.2 label/error/focus-visible states and --ino-target-comfortable on every control.

Use a select for a list of choices, radios for one visible choice, a checkbox for an independent option, and a toggle for an on/off setting. Keep labels visible. This demo checks only whether the email field is empty; application validation must also check format and server responses.

Modal

Use a modal for a focused decision that interrupts the current task. Give it a clear heading and an explicit cancel action. Focus-trapped, closes on Escape or backdrop click, restores focus to the trigger button on close.

Toast / inline alert / banner

One <ino-alert> shell, three layouts — inline, full-width banner, and stacked toast (via ToastService) — sharing the same closed info | success | warning | danger status union. info is the non-alarming register — it states a fact a reviewer should know without implying anything needs fixing, so real warnings keep their weight.

Use an inline alert next to the affected content, a banner for page-wide conditions, and a toast for brief feedback. Keep actionable errors visible near the control instead of relying on a transient toast.

Accessibility and implementation checklist

  • Tab through controls; check visible focus, readable labels and associated error text.
  • Open the modal with the keyboard, close with Escape, and confirm focus returns to its trigger.
  • Check narrow viewports, zoom, all three themes and reduced motion.
  • Consult each component's API and accessibility contract before integrating it. A demo is not a substitute for testing the complete application.
