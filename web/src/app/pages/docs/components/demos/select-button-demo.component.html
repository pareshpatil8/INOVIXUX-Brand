Variants — single, multiple, icon-only, equal-width

The component renders one <ino-select-button-option> per entry in options and takes no projected content, so the group can never drift out of sync with its value. multiple switches both halves of the contract at once (SPEC.md §2): off, the host is role="radiogroup" over native <input type="radio"> segments and a click replaces the selection; on, the host is role="group" over <input type="checkbox"> segments and a click accumulates. There is deliberately no aria-pressed in either mode — it is invalid on a checkbox and would double-announce against the native checked state. Click any group: the caption reads value back live.

States

disabled on the group disables every segment's native input, so the whole group leaves the tab order and drops to 60% opacity; a single option's own disabled flag does the same to that segment only while the rest of the group stays interactive — the case the group-level input cannot express. readonly keeps every segment focusable and fully legible (80% opacity, hover and pointer-down affordances withdrawn), then intercepts the native click so neither pointer nor arrow-key activation can move the selection. It is announced from whichever element is allowed to carry it: in single-select mode aria-readonly sits on the host, whose radiogroup role supports it, because the radio role does not — the rule ino-checkbox's SPEC.md §4 already settled, naming radio as its counter-example. In multi-select the host is role="group", which doesn't support it either, so there each segment's native checkbox role carries it instead. Hover and :focus-visible are live on every enabled group — tab into one for the focus ring, which is painted on the segment and raised above its neighbours' shared border.

There is no invalid/error state on this component, by decision rather than oversight (SPEC.md §10): a segmented control is selection-first UI — view modes, filters, toolbar state — where "invalid" does not apply, and the form-control case is better served by required on a backing field than by an inline error message. Reach for <ino-radio-group> when you need a validated one-of-N field.

Sizing — sm / default / lg

size is typed InoControlSize, a type alias — the manifest extractor records "values": null for that row, which is why the generated props table shows no enumerated values and the generic renderer produced no size row. The host's size class re-points four unsuffixed --ino-control-* aliases (height, inline padding, font size, gap) and the option's single set of declarations reads them, so one rule set serves three sizes across all three densities.

Note the heights these rungs resolve to here: this page runs in the dense register, so they are 28 / 32 / 40px, not the 36 / 44 / 52px of the fluid register — see the fluid pane in the next section, which does measure 44px. The contract's floor is that size="default" never drops below 32px even in dense mode, which is exactly what the middle rung does here.

Density is a global [data-density] token axis, not a per-component @Input(). Labels — accessible name, truncation, RTL

Two labelling patterns, both handled without the caller wiring ids by hand (SPEC.md §5). groupLabel renders a visible label above the group and points the host's aria-labelledby at it; ariaLabel names the group with no visible text, which is the right choice when surrounding copy already says what the group is for. An explicit ariaLabelledby beats both. The group name is separate from the per-segment name: each segment is named by its own label text, or by its ariaLabel when iconOnly hides that text.

groupLabel — visible, auto aria-labelledby

ariaLabel — named, no visible label

A segment's text truncates with an ellipsis rather than wrapping or pushing the group past its container — a segmented control that reflows to two lines stops reading as one control. The stylesheet is logical-properties-only (border-inline-start-width, border-start-start-radius, padding-inline), including the segment joints and the first/last corner radii, so the group mirrors correctly under dir="rtl": the first option keeps the leading corners on the right.

Dense-table usage

A two-segment per-row decision inside a dense table — the narrowest realistic placement for a segmented control, and the point at which it beats a pair of loose buttons: the row's state is always visible rather than inferred. These stay at size="default" rather than dropping to sm on purpose: in the dense register default resolves to exactly the 32px floor the accessibility contract promises, while sm would land at 28px — under the minimum target. Reach for size="sm" in a fluid-register layout (where it is 36px), not to squeeze an already-dense table.

Keyboard contract

Native input semantics, nothing custom — which is the whole reason the segments are real <input>s visually hidden inside their <label> rather than <button>s with hand-rolled ARIA.

Single-select is the standard radiogroup roving-tabindex behaviour the browser provides: Tab enters the group at the selected segment (or the first one if nothing is selected) and the next Tab leaves the group entirely — Arrow keys move and select within it, wrapping at both ends, and Space selects the focused segment. Multi-select is a group of independent checkboxes, so every segment is its own tab stop and Space toggles it; arrow keys do nothing there. disabled segments are skipped; readonly segments stay in the tab order and stay arrowable, but the intercepted click means focus moves without the selection following.
