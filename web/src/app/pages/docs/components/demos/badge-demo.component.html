Variants — dot, count, status

Three usage patterns per doc 26 §5: dot (simple presence indicator), count (numeric badge with 99+ overflow), status (labeled indicator with severity colors). Each variant has different accessibility semantics — see the A11y section below.

Count variant — 99+ overflow

When value >= 100, the displayed text is "99+" (per doc 26 §5 "max+ overflow"). The real value is always preserved in ariaLabel for screen readers.

@for (sample of countSamples; track sample.value) {

}

Status variant — severity colors

severity applies only to variant="status". Maps to semantic color roles (--ino-color-{{ '{' }}severity{{ '}' }} and --ino-color-{{ '{' }}severity{{ '}' }}-surface). Dot and count variants use fixed --ino-color-primary instead.

Sizing — sm/md (dense/fluid)

Two sizes per doc 26 §5 "sm/md" — aligned with dense/fluid density modes. Unlike ino-avatar's five-step scale, badge uses only two sizes: sm (dense mode — 8px dot, 16px count height, 20px status height) and md (fluid mode — 10px dot, 20px count height, 24px status height).

Positioned mode — badge on child element

Per doc 26 §5 "positioned-on-child or standalone" — when the parent container has position: relative, the badge anchors to the top-end corner via position: absolute. Mode is detected via :host-context() rather than an explicit prop. Positioned badges work on buttons, icons, avatars, etc.

Standalone mode — inline badge

Without a positioned parent, the badge renders as a regular inline element. Useful in toolbars, after labels, in lists, etc. No positioning logic applies.

Accessibility contract

Each variant has different a11y semantics per doc 26 §5:

  • Dot without ariaLabel: decorative, aria-hidden="true", no role. Pure visual indicator.
  • Dot with ariaLabel: informative, role="status", aria-label set. Announces the label (e.g. "Online") to screen readers.
  • Count: always informative, role="status", requires ariaLabel (e.g. "3 new notifications"). The visible count is aria-hidden to avoid double-announcement. The role="status" makes it a live region — dynamic count updates are announced automatically.
  • Status: the visible label is already accessible text, so no role or aria-label is added. Standard flow content semantics.

The "live-region guidance for dynamic counts" (doc 26 §5) is fulfilled by role="status" — it's already a polite live region, so incrementing value will announce the new count. No separate aria-live region needed.

States

Per doc 26 §5 "States: n/a" — badge has no interactive states (hover/focus/active) or validation states (invalid/error). It is a static visual indicator or counter, never a form control. The element it's attached to (e.g. a button) handles interaction; the badge is purely presentational.

Labels — RTL and wrapping

Logical properties only (padding-inline, inset-inline-end), so the component mirrors correctly under dir="rtl". Status variant labels wrap if constrained, though in practice they should be kept short (one or two words).

Mobile — React Native + Flutter ports

Per doc 26 §5 "Port both" — ino-badge will have equivalent React Native and Flutter implementations with the same variant/state coverage (dot/count/status, sm/md, severity colors, positioned/standalone modes). Mobile ports are in progress as separate deliverables.
