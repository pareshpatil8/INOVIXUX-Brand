Two forms, one implementation — enter/leave classes

Scroll inside the box. The first card carries [inoAnimateOnScroll] directly; the second wraps its content in <ino-animateonscroll> — same implementation via hostDirectives, so there is nothing to compare beyond the spelling. Both animate in with aos-rise, a keyframe animation whose from pose carries the hidden/offset state: before the first intersection the cards are fully visible in their natural CSS state, never pre-hidden. The first card also sets a leave class, aos-fall, so it re-animates on every pass (the default, repeat mode).

Once vs repeat — inoAnimateOnScrollOnce

Scroll the pair out of view and back a few times. The once card animates on its first reveal only — the observer disconnects there, the enter classes stay applied, and its counter can never pass 1. The repeat card re-animates on every re-entry because its enter class is genuinely removed on leave, which is what re-arms the CSS animation.

Threshold — inoAnimateOnScrollThreshold

Scroll slowly. The left card fires at threshold 0.15 — as soon as a meaningful sliver is inside the box. The right card waits for 0.9: nine tenths of it must be visible before its enter fires, so it animates noticeably later on the same scroll. inoAnimateOnScrollRootMargin shifts the same boundary geometrically instead — a positive margin starts the animation before the element arrives, a negative one delays it until the element is well inside.

Reduced motion

Under prefers-reduced-motion: reduce the directive applies no class and emits no event — the preference is re-read at every observer callback, so flipping the OS setting mid-session takes effect on the next scroll without a reload. Because the cards above are never pre-hidden, a reduced-motion visitor simply sees them, static, exactly where they would have animated to — and every counter on this page holds still, demonstrating that events and classes can never disagree. Flip the OS setting and scroll the boxes above to verify.
